## 摘要

USB 安全管理系统面向内网、专网、工业控制和敏感业务终端的 USB 外设安全管控场景。系统在 USB 外设与受控主机之间部署独立的 RK3568 硬件装置，在受控主机无需安装代理、驱动或业务软件的前提下，对 U 盘、键盘和鼠标执行设备识别、准入控制、恶意代码检测、文件访问控制、安全映射和关键业务审计。

系统的核心技术路线是将安全控制面从受控主机迁移到独立装置：真实 U 盘首先由装置识别和挂载，经 ClamAV 扫描后，由 Rust 服务构建受控虚拟 exFAT 文件系统，通过 NBD 发布为 Linux 块设备，再经 USB Gadget 映射给受控主机。受控主机访问的是装置生成的受控介质，而不是真实 U 盘分区。

本白皮书围绕系统采用的关键技术、技术选型依据、协作关系、安全机制、工程运行方式和适用边界展开，说明这些技术如何共同形成无代理的 USB 安全管控能力。硬件时序、介质兼容性和性能指标以目标 RK3568 环境的验收结果为准。

## 1. 技术背景与设计目标

### 1.1 技术背景

移动存储介质为隔离网络和离线环境提供了便捷的数据交换方式，同时也带来未经授权设备接入、恶意代码传播、可执行程序引入、敏感文件违规访问和操作不可追溯等风险。

传统终端代理方案依赖受控主机操作系统、驱动、权限和本地策略。在禁止安装软件、终端环境复杂、需要保持原系统完整性或同时管理 Windows/Linux 主机的场景中，代理方案会带来部署、兼容和持续运维成本。

USB 安全管理系统采用独立硬件中间层，在物理 USB 数据路径上执行安全控制，使受控主机只看到经过装置处理后的 USB 功能。

### 1.2 技术目标

系统围绕以下目标设计：

- 在受控主机零安装条件下实现 USB 外设安全管控；
- 基于 USB 描述符和接口能力识别设备，而非依赖可伪造的名称字符串；
- 未授权 U 盘不得映射，已授权 U 盘必须先扫描、后发布；
- 受控主机不能绕过策略直接访问真实 U 盘分区；
- 在统一受控视图中执行病毒、文件类型、可执行程序和读写权限控制；
- 支持允许范围内的文件与目录操作写回真实介质；
- 在挂载、扫描、NBD 或 Gadget 异常时执行失败关闭；
- 将账号、策略、授权、日志和安全判断集中在装置端；
- 在 ARM64 嵌入式平台上实现长期运行和离线交付。

### 1.3 核心设计原则

| 原则 | 技术含义 |
|---|---|
| 受控主机零安装 | 不依赖受控主机代理、驱动、浏览器插件或本地数据库 |
| 装置端权威 | 安全判断、策略、账号、授权和日志均以装置端为准 |
| 真实介质隔离 | USB mass-storage 只绑定受控 NBD，不直接绑定真实 U 盘 |
| 默认拒绝 | 未知、不支持或描述符能力不一致的接口不映射 |
| 失败关闭 | 关键处理阶段失败时不向受控主机发布设备 |
| 生命周期统一 | mount、扫描、虚拟介质、NBD 和 Gadget 由统一会话管理 |
| 数据最小化 | 管理端只维护进程内状态，不持久化业务数据 |
| 职责分离 | 系统管理、策略操作和日志审计采用三权分立模型 |

## 2. 总体技术架构

### 2.1 三节点架构

```text
USB 外设
   │ USB 接入
   ▼
┌────────────────────────────────────────────────────────────┐
│ USB 管控装置                                               │
│ RK3568 / ARM64 / Ubuntu 22.04 / Linux kernel 4.19         │
│ Rust 服务、ClamAV、SQLite、NBD、USB Gadget                 │
│ 设备识别、准入、扫描、策略执行、虚拟介质、审计和数据存储       │
└──────────────────┬────────────────────────────▲────────────┘
                   │ USB OTG                     │ TCP/TLS
                   ▼                             │ 私有协议
┌──────────────────────────┐       ┌─────────────┴───────────┐
│ 受控主机                  │       │ Windows 管理主机         │
│ Windows / Linux           │       │ Electron + Vue           │
│ 使用受控 U 盘和键鼠        │       │ 配置、维护、查询与展示     │
│ 无需安装系统软件           │       │ 不持久化业务数据           │
└──────────────────────────┘       └─────────────────────────┘
```

### 2.2 节点职责

| 节点 | 技术角色 | 主要职责 |
|---|---|---|
| USB 管控装置 | 安全执行点、协议服务端 | USB 识别、准入、扫描、策略执行、OTG 映射、鉴权、授权、审计和持久化 |
| Windows 管理主机 | 协议客户端、管理界面 | 连接装置、输入配置、选择文件、枚举管理主机 U 盘、展示结果 |
| 受控主机 | USB 功能使用方 | 使用装置发布的 U 盘、键盘和鼠标，不参与管理通信 |

### 2.3 双链路模型

系统包含两条相互独立的通信链路：

1. **管理链路**：管理端通过 TCP/TLS 私有协议连接装置，用于身份认证、策略配置、日志查询、授权和系统维护。
2. **USB 业务链路**：装置通过 USB OTG 向受控主机发布 mass-storage、keyboard HID 和 mouse HID 功能。

管理链路负责控制和配置，USB 业务链路负责向受控主机提供受控外设能力。受控主机不加入管理网络，也不持有装置管理凭据。

### 2.4 装置端技术分层

| 层次 | 主要技术 | 职责 |
|---|---|---|
| USB 接入层 | udev、sysfs、USB 描述符 | 热插拔发现、接口识别、设备能力判断 |
| 准入与扫描层 | 白名单、ClamAV | 存储准入、键盘验证、恶意代码检测 |
| 受控文件层 | Linux mount、虚拟 exFAT、策略引擎 | 读取真实文件树、构建统一视图、执行访问控制和写回 |
| 块设备与映射层 | NBD、configfs、USB Gadget | 将受控文件系统发布给受控主机 |
| 业务与数据层 | Rust 领域服务、SQLite | 用户、会话、策略、授权、日志和系统配置 |
| 协议层 | TCP、TLS、Protobuf、自定义帧 | 管理端连接、消息路由、鉴权和结果返回 |

### 2.5 核心技术链路

系统的核心价值来自多项技术沿 USB 数据路径协同工作，而不是单一组件：

```text
USB 外设接入
  → udev 发现与 USB 描述符识别
  → 白名单或 HID 准入
  → Linux 挂载真实介质
  → ClamAV 映射前扫描
  → 加载文件访问策略快照
  → 构建受控虚拟 exFAT
  → 通过 NBD 发布 /dev/nbdX
  → 绑定 USB mass-storage Gadget
  → 受控主机访问受控介质
```

其中，udev 和描述符解析解决“设备是什么”，白名单和键盘验证解决“设备能否进入”，ClamAV 解决“内容是否包含恶意代码”，虚拟 exFAT 和策略引擎解决“哪些内容可以访问”，NBD 和 USB Gadget 解决“如何以标准 U 盘形式交付给受控主机”。任何关键阶段失败，链路都不会继续发布。

## 3. 装置端系统软件技术

### 3.1 Rust

**应用位置：** 装置端常驻服务、USB 设备编排、文件系统控制、NBD 服务、协议网关、鉴权、审计和系统维护。

装置端需要长期管理文件描述符、挂载点、块设备、USB Gadget、Unix socket 和网络连接等系统资源。Rust 的所有权和类型系统能够在编译期约束资源生命周期与并发访问，降低内存越界、悬空引用和数据竞争风险。

相较于带垃圾回收的运行时，Rust 不依赖 GC 暂停，适合 HID 转发、块设备请求和异步网络等延迟敏感路径；相较于 C/C++，Rust 能在保持系统调用和原生性能能力的同时，提供更强的内存安全保障。

项目采用 Rust 2021 Edition，使用锁定工具链构建 ARM64 产物，通过 workspace 将协议、存储、扫描、文件访问、USB 识别、鉴权和审计等能力按领域拆分。

### 3.2 Tokio 异步运行时

**应用位置：** TLS 连接、协议请求、心跳、USB 事件编排、扫描任务协调和服务生命周期。

Tokio 为装置端提供异步 I/O、任务调度、超时和取消能力，使单个服务能够同时处理管理端连接、设备事件和后台任务。阻塞式系统调用或外部进程调用与异步协议处理隔离，避免长时间扫描或文件操作阻塞管理链路。

### 3.3 Linux 系统能力封装

装置端通过 Linux 原生能力访问 USB、文件系统和块设备：

- udev 与 sysfs 用于设备发现和描述符信息获取；
- mount/umount 用于真实 U 盘文件系统接入；
- NBD 用于提供用户态虚拟块设备；
- configfs 与 USB Gadget 用于发布受控 USB 功能；
- evdev 用于读取键盘、鼠标输入事件；
- Unix socket 用于调用 ClamAV 守护进程；
- systemd 用于服务启动和异常重启。

Rust 模块对上述系统资源进行封装，业务层通过明确接口使用系统能力，便于在无真实硬件条件下进行逻辑测试。

## 4. USB 识别与准入技术

### 4.1 udev 事件与启动枚举

装置端结合两种方式发现 USB 接口：

- 服务启动时枚举已经存在的 USB 设备，避免服务重启后遗漏已插入设备；
- 运行期间订阅 udev add/remove 事件，处理设备热插拔。

事件源将 Linux 设备信息转换为内部统一事件，再交由设备编排层执行识别和准入。设备拔出事件用于结束验证、停止扫描、卸载文件系统和释放映射资源。

### 4.2 基于描述符的接口识别

USB 设备名称、厂商字符串和产品字符串可以由设备固件任意填写，不能作为安全准入依据。系统综合使用以下信息识别接口：

- 设备描述符和配置描述符；
- USB interface class、subclass 和 protocol；
- 输入/输出端点类型与方向；
- 接口能力与声明类型的一致性；
- 设备序列号、VID/PID 等标识信息。

识别以 USB interface 为最小处理单位。复合设备的不同接口分别判断：受支持接口进入对应链路，不支持或能力不一致的接口默认拒绝。

### 4.3 大容量存储准入

普通大容量存储接口识别通过后，装置根据白名单执行准入。白名单记录设备序列号、VID/PID、名称、容量、描述、添加来源和只读/读写权限。

白名单只参与已经识别为普通大容量存储的接口判断，不会把键盘、鼠标或未知接口转换为存储设备。准入成功后，设备进入独立存储会话，依次完成挂载、扫描、策略快照、虚拟介质构建和发布。

### 4.4 键盘与鼠标准入

键盘输入由装置通过 evdev 接管。用户按顺序输入 `1`、`2`、`3`、`4` 完成验证，验证期间的按键不向受控主机透传；验证成功后，装置通过 keyboard HID Gadget 建立映射。

鼠标接口识别通过后自动映射为 mouse HID Gadget。键鼠拔出时，装置释放输入状态、转发任务和 Gadget 资源。

### 4.5 技术价值

基于接口能力的识别和分类准入，使设备名称伪装无法直接获得访问权限；接口级处理能够约束复合设备中的非预期功能；默认拒绝策略保证无法可靠识别的设备不会进入受控主机。

## 5. 恶意代码检测技术

### 5.1 ClamAV 与 clamd

**应用位置：** 已准入 U 盘映射前的全盘扫描。

系统采用 ClamAV 作为恶意代码检测引擎。ClamAV 支持 ARM64 和离线病毒库，能够部署在无互联网连接的装置环境中。装置使用常驻 `clamd` 守护进程加载病毒库，并通过 Unix socket 调用扫描能力，避免每次任务重复启动引擎和加载病毒库。

### 5.2 扫描链路

```text
白名单准入
  → 挂载真实 U 盘
  → 调用 clamd 全盘扫描
  → 生成病毒文件路径集合
  → 写入恶意代码检测日志
  → 构建受控虚拟介质
```

扫描结果分为无风险、发现病毒和扫描失败。病毒文件路径作为虚拟文件系统构建输入，用于生成受控显示和阻断语义。clamd 不可用、病毒库不可用、扫描异常或 I/O 失败时，存储会话不继续发布。

### 5.3 病毒文件处理

病毒命中文件在受控视图中使用安全前缀标识，不向受控主机返回真实文件内容，也不修改真实 U 盘中的原始文件名和内容。扫描结果和病毒信息记录在装置端恶意代码检测日志中。

### 5.4 技术边界

全盘扫描时长与介质容量、文件数量、文件类型、病毒库规模和 RK3568 性能相关。ClamAV 由目标设备基础镜像提供，系统安装包验证其可执行程序、守护进程、socket 和病毒库运行契约。

## 6. 受控存储虚拟化技术

### 6.1 技术挑战

受控主机需要像使用普通 U 盘一样访问文件，但不能接触真实分区。装置还需要兼容多种真实文件系统、应用文件策略、支持大文件，并在本地存储有限的条件下避免复制完整介质镜像。

系统采用以下组合方案：

```text
真实 U 盘分区
  → Linux 文件系统挂载层
  → Rust 受控虚拟 exFAT
  → Linux NBD /dev/nbdX
  → USB f_mass_storage Gadget
  → 受控主机
```

### 6.2 Linux 挂载层

真实 U 盘分区挂载到会话隔离目录：

```text
/mnt/usb-control/raw/<session-id>
```

Linux 内核驱动或用户态挂载工具负责解释真实文件系统，Rust 服务通过统一目录树访问文件。目标文件系统包括 FAT32、exFAT、NTFS、ext2、ext3 和 ext4，实际可用范围取决于装置系统镜像启用的驱动和工具。

挂载层将不同真实文件系统统一为目录与文件接口，使后续扫描和虚拟介质构建不需要分别实现各类磁盘文件系统解析器。

### 6.3 虚拟 exFAT 文件系统

**应用位置：** 真实文件树与 NBD 块设备之间的受控文件系统层。

装置读取真实挂载目录的完整递归目录树，在内存中构建虚拟 exFAT 状态，包括：

- 引导区和卷参数；
- FAT 簇链；
- allocation bitmap；
- 目录项和长文件名；
- 文件与目录的簇分配；
- 文件内容到虚拟扇区的映射；
- 写事务和元数据 overlay。

选择 exFAT 作为输出格式，主要基于以下原因：

- Windows 和 Linux 可使用标准 mass-storage 方式访问；
- 支持超过 4 GiB 的单文件；
- 文件系统结构相对适合动态生成和解释；
- 可将多种真实文件系统转换为统一受控视图。

受控视图不承诺保留原始文件系统类型、NTFS ACL、Linux 权限位、属主属组、符号链接、硬链接、特殊文件和扩展属性等高级语义。

### 6.4 Linux NBD

**应用位置：** 将 Rust 用户态虚拟文件系统发布为 Linux 块设备。

NBD 将 `/dev/nbdX` 的块请求转发给用户态服务。Rust NBD 服务按 LBA 处理 READ、WRITE 和 FLUSH 请求，并调用虚拟 exFAT 后端生成或接收扇区数据。

选择 NBD 的主要原因是：

- Linux kernel 4.19 原生支持；
- `f_mass_storage` 可以绑定 `/dev/nbdX`；
- 文件内容可以按需从真实挂载目录读取；
- 不需要在装置 32 GB 本地存储中生成完整镜像；
- 便于在用户态实现虚拟文件系统和策略控制。

未采用 ublk，是因为该技术需要更高版本 Linux 内核；未采用完整镜像加 loop，是因为本地存储无法为大容量 U 盘保留等容量副本。

### 6.5 USB mass-storage Gadget

装置通过 configfs 创建 USB Gadget，并使用 `f_mass_storage` 向受控主机发布 U 盘功能。LUN 只绑定受控 `/dev/nbdX`，禁止直接绑定真实 `/dev/sdX` 或其分区。

这一约束建立了受控主机与真实介质之间的技术隔离：来自受控主机的所有块访问都必须经过 NBD 和虚拟 exFAT 层。

### 6.6 写事务与真实介质同步

受控主机修改 exFAT 时，会分别写入 FAT、allocation bitmap、目录项和文件数据。系统将相关扇区写入收集为事务，解析出文件或目录的新建、修改、删除、重命名、扩容和截断操作。

当设备具有读写权限且操作未命中策略时，完整事务提交到真实挂载目录；未完成或无效事务不会提前更新已提交视图。只读设备在真实挂载层和 Gadget 发布层同时执行写保护。

## 7. 文件访问控制技术

### 7.1 策略模型

文件访问控制由以下策略共同组成：

- 病毒文件阻断；
- 可执行程序访问控制；
- 文件类型黑名单；
- 介质自动读取控制；
- U 盘只读/读写权限。

策略按照固定优先级短路判断：

```text
病毒文件
  → 可执行程序
  → 文件类型黑名单
  → 介质自动读取
  → 读写权限
```

### 7.2 会话策略快照

U 盘进入存储链路时，装置获取当时的白名单权限和文件访问策略，形成该会话的策略快照。映射期间的管理端配置变化不会改变已建立会话的判断结果，设备重新插拔后使用最新策略。

这种设计避免同一次 U 盘使用过程中出现前后不一致的访问语义，也使 NBD 请求路径无需反复读取数据库。

### 7.3 受控内容表达

病毒或策略命中文件仍可在受控目录中表达，但不向受控主机暴露真实内容，也不允许通过改名、删除或写入改变真实文件。受控视图使用安全文件名或占位内容表达阻断结果，使用户能够识别文件存在，同时避免真实数据泄露。

普通未阻断文件按需读取真实内容；允许写入时，受控主机的文件系统操作经过事务解释后同步到真实介质。

### 7.4 技术价值

策略执行位于装置端虚拟存储链路，不依赖受控主机进程、文件系统过滤驱动或本地权限配置。即使受控主机没有安装管控软件，也无法绕过 NBD 和虚拟文件系统访问真实分区。

## 8. 管理通信技术

### 8.1 TCP/TLS 私有协议

**应用位置：** Windows 管理端与 USB 管控装置之间的管理链路。

管理端主动建立 TCP 连接，装置默认监听 `9600` 端口。链路通过 TLS 加密，业务消息采用自定义二进制帧承载 Protobuf 载荷。

协议帧包含魔数、消息类型、请求序列号、载荷长度和 CRC32。序列号用于匹配并发请求与响应，长度字段用于消息边界和资源限制，CRC32 用于载荷一致性校验。连接层还提供超时、心跳和异常帧处理。

### 8.2 Protocol Buffers

Protobuf 用于管理命令、响应和业务数据序列化。装置端通过 `prost` 生成 Rust 类型，管理端通过 `protobufjs` 生成 TypeScript/JavaScript 类型，双方共享 `proto/usb_control.proto`。

选择 Protobuf 的原因包括：

- 二进制编码紧凑，适合文件和分页数据传输；
- 字段类型明确，减少两端解释差异；
- 支持兼容性演进；
- Rust 和 Node.js 均具备成熟实现。

### 8.3 TLS 与证书指纹

装置持有 TLS 服务端证书和私钥，管理端安装包包含对应证书的 SHA-256 指纹。连接时管理端验证证书指纹，不匹配时拒绝建立受信任业务通道。

TLS 提供链路机密性，证书指纹用于验证对端使用受信服务证书及管理端与装置端的版本配套关系。该机制不用于区分同一产品版本下的单台装置。账号、角色、授权状态和业务权限继续由装置端应用层校验，网络加密、受信证书验证与业务鉴权共同构成管理链路安全边界。

### 8.4 会话与心跳

登录成功后，装置签发随机会话 token。会话状态只保存在两端进程内存中，不持久化，并具备空闲超时和显式失效机制。业务请求携带 token，装置在路由处理前执行会话和角色权限校验。

心跳用于发现失效连接并维护连接状态，不代替业务会话鉴权。管理端重新连接后重新确认装置授权状态和用户会话有效性。

## 9. 装置端数据与审计技术

### 9.1 SQLite

**应用位置：** 装置端账号、角色、白名单、策略、授权状态、系统配置和业务日志持久化。

SQLite 以嵌入式单文件方式运行，不需要独立数据库服务，适合离线嵌入式设备。项目使用 `rusqlite` 并静态集成 SQLite，减少目标设备动态库依赖。

SQLite 事务用于保证用户管理、策略导入和多表业务操作的一致性。数据库 schema 通过 migration 和版本号管理，安装及安装包覆盖升级时执行迁移。

### 9.2 数据权威边界

装置端是业务数据的唯一权威来源：

- SQLite 保存账号、授权、白名单、文件访问策略和三类业务日志；
- 本地文件系统保存病毒库、安装配置、密钥材料和运行日志；
- 管理端只在进程内保存当前连接、会话和查询结果；
- 管理端不使用 SQLite、localStorage 或 IndexedDB 保存业务数据。

这一设计保证同一装置连接不同管理主机时，账号、策略和日志保持一致，并减少管理主机上的敏感数据残留。

### 9.3 三类业务日志

| 日志类别 | 记录范围 |
|---|---|
| USB 审计日志 | 受支持 U 盘、键盘和鼠标的接入、准入、验证、映射、拔出及失败结果 |
| 恶意代码检测日志 | 扫描任务、扫描结果、病毒名称、命中文件和失败分类 |
| 操作日志 | 登录、用户、白名单、策略、授权、升级和日志管理操作 |

日志支持条件查询、分页、导出和按保留期清理。装置整体存储使用率达到阈值后，写入哪类日志只滚动覆盖该类别最旧记录，避免跨类别删除。

Rust 服务运行日志用于工程排障，按模块分组并按文件大小滚动，不属于管理端可查询的业务日志。

## 10. 身份、权限与密码技术

### 10.1 三权分立

系统定义系统管理员、操作员和审计员三类角色：

| 角色 | 技术权限范围 |
|---|---|
| 系统管理员 | 用户、授权、系统升级、病毒库升级和设备描述 |
| 操作员 | U 盘白名单、文件访问策略和策略包 |
| 审计员 | 三类业务日志的查询、导出和合规清理 |

管理端路由和页面根据角色控制可见能力，装置端协议中间件对每个业务请求执行最终鉴权和授权。前端菜单隐藏不是安全边界。

### 10.2 密码与账号保护

密码在装置端使用 bcrypt 哈希保存，不存储明文。登录失败计数和临时锁定机制用于限制连续口令尝试；修改密码、重置密码、删除用户等操作会使相关会话失效。

内置账号不可删除，用户管理和密码操作均由装置端执行字段校验、权限判断和操作审计。

### 10.3 离线授权

系统适用于无法访问互联网的网络环境，通过装置机器码与离线授权文件完成许可管理。授权文件使用 SM2 数字签名，装置侧仅部署验证公钥，按签名、机器码和有效期验证授权。

授权状态由装置端持久化并作为登录后业务访问的前置条件，管理端不能通过本地状态绕过授权判断。

## 11. 国密策略文件保护技术

### 11.1 应用场景

白名单和文件访问策略可以导出为 `.bin` 文件，用于离线备份和装置间策略迁移。策略内容包含设备标识与安全规则，需要同时防止明文泄露、内容篡改和伪造。

### 11.2 SM2、SM3 与 SM4

策略文件组合使用国产密码算法：

| 算法 | 用途 |
|---|---|
| SM4 | 对策略内容进行对称加密，保护机密性 |
| SM3 | 计算策略摘要，检测内容损坏或篡改 |
| SM2 | 对策略数据签名并在导入时验签，验证文件来源和完整性 |

策略包包含文件魔数、版本、算法标识、随机 IV、密文、摘要和签名。导入时依次校验文件结构、版本、算法、签名和摘要，再解密并反序列化策略。

### 11.3 原子导入

策略导入采用整体替换语义，不进行增量合并。只有文件验证、解密、数据校验和数据库写入全部成功后，新策略才生效；任一步骤失败时原策略保持不变。

## 12. 安全架构

### 12.1 威胁与技术机制

系统围绕设备伪装、介质绕过、恶意代码、未授权管理和敏感数据残留等风险建立纵深防护：

| 主要风险 | 技术机制 | 安全结果 |
|---|---|---|
| USB 名称或产品字符串伪装 | 描述符、接口类型、协议号和端点能力联合识别 | 名称伪装不能直接获得准入 |
| 未授权 U 盘接入 | 存储接口识别、白名单和权限判断 | 未准入介质不向受控主机发布 |
| 恶意代码传播 | ClamAV 映射前全盘扫描、病毒文件受控表达 | 扫描异常时失败关闭，病毒内容不暴露 |
| 绕过文件访问策略 | 真实分区隔离、虚拟 exFAT、NBD、受控 Gadget | 主机不能直接访问真实 U 盘分区 |
| 未授权管理操作 | 账号认证、会话 token、三权分立、服务端权限校验 | 页面限制与装置端强制授权共同生效 |
| 管理链路窃听或非受信服务接入 | TLS 加密和证书 SHA-256 指纹校验 | 管理数据加密传输并验证受信服务证书 |
| 策略文件泄露或篡改 | SM4 加密、SM3 摘要、SM2 签名 | 非法或损坏策略包拒绝导入 |
| 授权文件伪造 | 机器码绑定、SM2 签名和有效期校验 | 未通过验证的授权不生效 |
| 管理主机敏感数据残留 | 管理端零业务持久化 | 账号、策略、日志和 token 不落盘 |
| 安全事件不可追溯 | USB、恶意代码和操作三类业务日志 | 关键业务行为可查询和导出 |

### 12.2 安全执行边界

装置端同时承担策略执行点、身份验证点和业务数据权威源。管理端负责输入和展示，但不能以本地页面状态替代装置端判断；受控主机只使用装置发布的标准 USB 功能，不能访问管理协议或真实介质。

安全控制采用分层组合：设备层决定接口是否准入，内容层完成病毒扫描，文件层执行访问策略，块设备层保证所有主机 I/O 经过受控路径，协议层执行管理身份和权限验证，数据层记录结果与审计信息。

### 12.3 密钥与敏感数据边界

- TLS 私钥只部署在装置端，管理端仅持有证书指纹；
- 授权签发私钥不进入产品运行环境，装置端只部署验证公钥；
- 策略密码材料部署在装置端，不写入管理端代码和业务日志；
- 密钥文件、数据库和业务数据目录使用受限文件权限；
- 管理端退出后，连接状态、会话和查询结果随进程内存释放。

## 13. 管理端技术体系

### 13.1 Electron 32

**应用位置：** Windows 桌面管理程序的运行容器和原生能力层。

Electron 同时提供 Chromium 页面运行环境和 Node.js 桌面能力，适合本系统对本地文件选择、管理主机 USB 枚举、TLS socket、窗口生命周期和 Windows 安装包的需求。

管理端需要选择策略文件、授权文件、系统升级包和日志导出目录，并需要枚举管理主机本地 U 盘。这些能力超出普通浏览器沙箱范围，因此采用桌面客户端而非纯 Web 页面。

### 13.2 Vue 3 与 TypeScript

Vue 3 用于构建登录、U 盘管理、文件访问控制、策略、日志、系统、授权和用户管理页面。Composition API 和组件化结构用于复用表格、对话框、连接提示和操作反馈。

TypeScript 为 IPC、协议响应、页面服务和状态管理提供静态类型约束，与 Protobuf 生成类型共同降低字段不一致风险。

### 13.3 Pinia、Vue Router 与 Element Plus

- **Pinia**：维护连接状态、当前用户、角色、授权状态和页面数据等进程内状态；
- **Vue Router**：组织页面导航并执行登录、授权和角色路由守卫；
- **Element Plus**：提供表格、表单、分页、弹窗和消息反馈等桌面管理界面组件。

### 13.4 Electron 进程隔离

管理端采用主进程、preload 和渲染进程分层：

- 主进程负责 TLS、本机 USB 枚举、原生文件对话框和窗口管理；
- preload 通过受控 IPC 暴露最小桌面能力；
- 渲染进程只处理页面、状态和用户交互；
- IPC handler 校验可信发送方和文件访问范围。

该结构避免渲染页面直接获得完整 Node.js 和文件系统权限，缩小桌面应用攻击面。

### 13.5 Windows 交付

管理端使用 electron-builder 生成 NSIS 安装包，支持 Windows 10 1809 及以上版本和 Windows 11。安装包包含 Electron Runtime、Vue 资源、主进程代码和证书指纹，不要求现场安装 Node.js 或浏览器环境。

管理端安装包不包含装置端 TLS 私钥、授权签发私钥、策略密钥、ClamAV 文件、默认设备地址、账号、密码、会话信息或业务数据。

## 14. 可靠性与资源生命周期技术

### 14.1 StorageSession

每个已准入大容量存储设备对应独立存储会话。会话统一拥有以下资源：

- 真实介质挂载点；
- ClamAV 扫描任务；
- 策略快照和虚拟文件系统；
- NBD 设备和请求任务；
- USB mass-storage Gadget LUN；
- 设备运行状态和失败信息。

统一所有权保证资源按照确定顺序创建和逆序释放，避免不同模块分别清理同一 mount、NBD 或 Gadget。

### 14.2 失败关闭

以下任一阶段失败时，系统停止后续发布并释放已创建资源：

- 白名单和权限判断；
- 真实文件系统挂载；
- ClamAV 扫描；
- 虚拟 exFAT 构建；
- NBD 设备发布；
- USB Gadget 绑定和枚举。

失败关闭保证安全检查异常不会退化为直接放行。

### 14.3 启动恢复与拔出清理

装置服务启动时幂等准备 USB Gadget 基线，并清理遗留的 raw mount、NBD 连接和 Gadget LUN。设备拔出、服务停止和异常路径通过会话标识释放对应资源，避免过期任务影响新的设备会话。

### 14.4 systemd 与运行日志

主服务由 systemd 管理，支持开机启动和异常退出后的自动重启。运行日志使用 tracing 记录，并按 USB、协议、系统和审计等模块分组滚动，便于定位硬件、协议和业务问题。

## 15. 部署与兼容性

### 15.1 装置端部署

| 项目 | 技术基线 |
|---|---|
| 硬件 | RK3568 / ARM64 / 4 GB RAM / 32 GB 本地存储 |
| 操作系统 | Ubuntu 22.04 |
| Linux 内核 | 4.19 |
| 交付格式 | Debian ARM64 安装包 |
| 关键依赖 | configfs、USB Gadget、NBD、ClamAV、目标文件系统驱动 |

安装包包含 ARM64 Rust 二进制、systemd unit、配置模板、数据库 migration、TLS 资源、策略密钥和部署检查脚本。安装过程校验操作系统、内核、ClamAV、证书和密钥等运行契约，并初始化数据库和服务。

ClamAV 可执行程序、守护进程和病毒库由目标设备基础镜像提供，安装包不在线下载系统依赖。

### 15.2 数据库迁移

装置端提供独立数据库 migration 工具，根据 `PRAGMA user_version` 顺序执行随安装包交付的迁移。迁移完成后更新系统版本，保证首次安装和安装包覆盖升级使用一致的数据库初始化路径。

### 15.3 系统与病毒库升级

系统升级数据由管理端上传，装置执行 SHA-256 一致性检查和版本检查后完成文件替换、版本更新与服务重启。运行时系统升级不执行数据库迁移；数据库结构变化随 Debian 安装包迁移流程交付。

病毒库升级数据由管理端上传，装置校验版本规则和数据一致性后更新 ClamAV 病毒库，并记录病毒库版本和更新时间。

### 15.4 环境兼容性

装置端运行依赖 Linux kernel 4.19 的 configfs、USB Gadget、NBD 和目标文件系统驱动。管理端运行于 Windows 10 1809 及以上版本或 Windows 11；受控主机可使用 Windows 或 Linux 的标准 USB mass-storage 和 HID 驱动，无需安装本系统软件。

真实介质文件系统、USB 控制器、UDC 枚举和主机缓存行为具有环境相关性，需要在交付使用的 RK3568 系统镜像、U 盘型号和受控主机组合上确认兼容性。

### 15.5 部署自检

交付阶段通过部署自检验证装置服务、数据库、管理通信、密钥文件权限和恶意代码检测环境，确认安装包与目标系统镜像满足运行契约。具体检查步骤由部署手册和随安装包提供的检查工具定义。

---

## 16. 性能与容量设计

### 16.1 无完整镜像设计

系统不在装置本地存储中复制完整 U 盘镜像。虚拟 exFAT 元数据和写事务状态主要保存在内存，文件内容按需从真实挂载目录流式读取或写回。

该方案使 32 GB 装置能够处理容量大于本地存储的 U 盘，并减少映射前的数据复制时间和本地闪存写入。

### 16.2 大文件支持

受控输出采用 exFAT，可表达超过 4 GiB 的单文件。文件数据按虚拟簇和扇区映射到真实文件偏移，不要求将大文件整体加载到内存。

### 16.3 性能影响因素

系统实际性能受以下因素共同影响：

- U 盘接口速率、介质性能和碎片情况；
- 文件数量、目录深度和单文件大小；
- 真实文件系统驱动与挂载工具；
- ClamAV 病毒库规模和扫描特征；
- NBD 请求粒度与受控主机缓存策略；
- RK3568 CPU、内存和 USB 控制器性能。

全盘扫描时长、虚拟 exFAT 大文件吞吐和 USB 枚举时延应在交付使用的 RK3568、系统镜像、U 盘和受控主机组合上测量。

---

## 17. 技术适用边界

1. 系统当前管控普通大容量存储、键盘和鼠标接口，其他 USB 接口默认不映射。
2. 真实文件系统支持范围取决于目标系统镜像启用的内核驱动和挂载工具。
3. 受控主机看到统一虚拟 exFAT 视图，不完整保留原文件系统的 ACL、权限位、链接和扩展属性。
4. 病毒扫描采用映射前全盘扫描，设备可用时间随介质容量、文件数量和硬件性能变化。
5. 管理端与装置之间需要 IP 网络可达，受控主机不需要加入管理网络。
6. 管理端不承担业务数据备份职责，不持久化装置账号、策略、日志和会话。
7. USB Gadget 枚举、NBD 时序和受控主机表现与目标硬件及操作系统相关。
8. 系统提供 USB 技术管控能力，不能替代组织层面的介质审批、数据分类、人员管理和物理安全制度。

---

## 18. 结语

USB 安全管理系统通过独立硬件执行点，将 USB 设备识别、准入控制、恶意代码检测、文件访问控制、安全映射和审计从受控主机环境中解耦。

系统以 Rust 管理系统资源和业务服务，以 udev 与 USB 描述符完成接口识别，以 ClamAV 执行映射前检测，以 Linux mount、虚拟 exFAT 和 NBD 构建受控存储视图，再通过 USB Gadget 向受控主机发布标准 USB 功能；管理端通过 Electron/Vue 提供桌面交互，并使用 TLS、Protobuf、会话鉴权和装置端权限校验建立安全管理通道。

这些技术并非孤立使用，而是沿 USB 接入、内容检查、受控虚拟化、主机映射和行为审计形成连续技术链路，在保持受控主机零安装的同时，使安全策略在真实介质与受控主机之间得到统一执行。
